# Windows updates

The existing 0.1.0 installation needs one reviewed bootstrap installer to gain the updater. Subsequent versions are checked through **Settings → Application updates → Check for Updates**, downloaded in-app, and installed only after **Review installation** plus a native confirmation. Cancel is the default. Plain browser and development sessions cannot install.

The fixed trust policy verifies GitHub Actions Sigstore provenance for `khapung280/Agents` before accepting release metadata. The signed manifest binds stable version, source commit, compatibility, notes, installer filename, size and SHA-256. A checksum alone is not publisher authentication. The renderer cannot provide URLs, paths, commands, roots or approvals. Version floors and accepted-manifest hashes prevent downgrade and same-version replacement.

Only restricted GitHub HTTPS endpoints are used. Downloads have time/size limits, cancellation, progress and private partial files. Bytes are checked again before installation. The main process preserves Windows Internet-zone metadata and opens the installer normally through the Windows shell, after stopping and draining local workers. No silent flags, elevation, security-policy changes or SmartScreen exceptions are used. Shell acceptance is pending, not successful installation; the expected version must subsequently start a healthy local service. Uncertain attempts never replay automatically.

The app remains **unsigned in Windows**. Sigstore authenticates the GitHub build; it is not an Authenticode certificate or SmartScreen reputation. Organization policy may block this preview. Use its review/signing process; never disable protection. Initial installation and embedded roots must come from a trusted source. Unknown trust-root rotation or stale signed metadata requires an owner-reviewed bootstrap update rather than bypassing verification. Same-user tampering and a compromised authorized publisher are outside the updater's protection.

Application files use versioned installation directories. Staging failure retains the old shortcut/version. Personal data remains under the existing Electron `agents-data` directory, normally `%APPDATA%\ULTIMATE AGENTS — BOTH\agents-data`. Database, memories, workflows and `windows-policy.json` are not replaced. Update metadata/downloads have their own `agents-data\updates` subdirectory. No new permission is granted. The installer does not migrate or roll back personal data.

After network failure, retry the check/download manually. After signature or checksum failure, investigate the release; do not override verification. If Windows refuses installation, review its decision. If the new application fails to start, close it and review data compatibility before explicitly using the retained previous version. There is no automatic downgrade or database rollback.

Main-branch CI prepares and verifies artifacts and provenance. It does not publish a Release. The separate publication workflow is triggered by an explicitly approved version tag, consumes the exact successful main-build artifact, and refuses replacement of existing releases/assets.

Controller tests use labeled network/installer fixtures; cryptographic tests separately exercise signatures. Windows CI checks native compilation and real isolated installation/upgrade behavior. Laptop acceptance still requires normal Windows prompts, an approved upgrade, restart into the new version, and checks of memory/policy/permissions. No production-security or real-device claim follows solely from cloud tests. No OpenAI key or paid model call is involved.
